# Intent — CHG-0033 Forge Experience Report Markdown

## Summary

Add a deterministic Markdown projection for every canonical Forge Experience
Report (FER), while keeping the existing YAML report as the only source of
truth for Forge tooling.

## Problem

FER currently preserves useful structured evidence at
`dogfooding/reports/FER-####.yml`, but contributors must read YAML directly to
review context, observations, evidence, positive evidence, and follow-ups.

## Desired Outcome

Each canonical report can have a sibling Markdown file generated from the
canonical YAML. The generated document is concise, hierarchical, safe for
GitHub/editor review, deterministic, and regenerated by official FER writes.

## Scope

- Add a pure renderer for the existing `forge/experience-report@1` shape.
- Keep `dogfooding/reports/FER-####.yml` as canonical data.
- Generate a collision-free sibling projection without changing FER layout.
- Add explicit regeneration for one report and all historical reports.
- Cover creation, append/update, historical reports, optional fields,
  deterministic output, drift handling, and Markdown write failure.
- Update FER contributor documentation and the realistic example artifact.

## Out of Scope

No FER lifecycle, opt-in boundary, taxonomy, provenance collection,
observation semantics, storage location, Protocol schema, Harness integration,
telemetry, HTML/PDF output, bidirectional editing, or Markdown-to-YAML parser.

## Success Criteria

- Canonical YAML remains the sole semantic input to tooling.
- Valid reports render readable context, observations, positive evidence, and
  follow-up candidates using only present fields.
- Re-rendering identical input produces byte-identical Markdown and no diff.
- Official record and explicit render operations keep projections current.
- Missing Markdown does not invalidate historical or disabled FER workflows.
- Markdown failure is reported honestly and never corrupts canonical YAML.
